## 1. 选型需求(硬性约束)

来自本研究网络的实际拓扑(Task 1 实测 + plan):

| # | 需求 | 原因 | 优先级 |
|---|---|---|---|
| 1 | ≥2× 10G **SFP+** 口 | Mac en11 与 M4 均为 Intel X520(SFP+),现用 **DAC 直连线,若交换机是 SFP+ 口,现有 DAC 直接复用**,零线缆成本 | ★★★ |
| 2 | ≥1× 10G **RJ45 电口** | NAS(绿联 DXP4800 Plus,AQC113 10G 电口);理想是 2 个(小米万兆路由器上联也是 10G 电口) | ★★★ |
| 3 | 下联 1G/2.5G 若干 | Wi-Fi AP、IoT 均为千兆/百兆;电口多速率向下兼容可直接接,或另配 2.5G 交换机级联 | ★ |
| 4 | 上联 10G | 小米万兆路由器(10G 电口) | ★★ |
| 5 | **Jumbo ≥ 9K 帧** | 覆盖本栈现实档 **2034**(Mac X520 驱动上限)与「供他机参考档 9000」(NAS AQC113 maxmtu 16334);datasheet 明确写 9216/9600/12K/16K 才算数 | ★★★ |

**jumbo 把关规则**(本次调研执行):仅写「jumbo」不写数值 → 要求进一步证据;产品页/spec 无 jumbo 字样 → 标记「需客服确认」甚至直接否决(TP-LINK 官方 FAQ 明文:spec 未声明 jumbo = 最大 1522B,见附录链接 8)。

## 2. 候选全景与排除说明

调研覆盖品牌(任务点名 + 补充):TP-LINK/普联、水星 Mercury、华为、H3C、锐捷、绿联 UGREEN、MikroTik、铁威马 TerraMaster、海康威视、兮克 XikeStor、中兴。

**结构性排除**(均经官网产品线核实):

- **华为 / H3C / 锐捷**:无家用桌面万兆形态。华为 S 系列企业机(万兆上行)起步 24 口带风扇机架式,千元级只有千兆;H3C Mini 系列止步 2.5G(H3C Mini 最高 8×2.5G+上行);锐捷睿易家用线同理。企业级 4×SFP+ 机型(如华为 S5735)二手虽便宜(~¥500-800)但风扇噪音 + 无保修,不符合「家庭静音」目标,本次不推荐(想要折腾可在闲鱼自行淘企业二手,注意 jumbo 参数企业机通常 ≥12K)。
- **海康威视**:DS-3E 系列全部为百兆/千兆 PoE 监控向(官网产品线核实),无家用万兆桌面机 → 排除。
- **铁威马 TerraMaster**:官网产品线只有 NAS/直连存储,无交换机产品 → 排除(任务清单中的候选,核实后剔除)。
- **小米 / 中兴**:小米无独立交换机产品线(只有路由器);中兴家用网络无万兆桌面交换机 → 排除。
- **MikroTik CRS305-1G-4S+IN**(4×SFP+):海外 $149 很香,但**国内渠道溢价严重**(天猫 ¥1589 起、京东 ¥1683–2587,见附录链接 18),且无 10G 电口、售后依赖代购 → 对比表留档,不作推荐。
- **水星 Mercury**:普联集团性价比品牌,但现有产品线止步于 SE109/SE106(8×2.5G 电 + 1×SFP+ 上行)形态(官网核实),适宜做下联补充交换机而非核心万兆机。
- **兮克 SKS8300-8T**(8×10G 全电口,jumbo 12K 官网实锤,¥1647–1881):端口形态与 Mac/M4 的 **X520(光口)不匹配**(X520 无电口),排除主推,对比表留档。

**晋级正选**:绿联、兮克、TP-LINK 三家的 4 个机型 + 1 个反面警示机型。

1. **端口形态与需求逐条对上**:2 根 X520 DAC 进 SFP+、NAS AQC113 与小米万兆各占一个 10G 电口、剩 2 电 2 光全空余,是本次调研唯一「形态完全命中」的机型。
2. 电口是多速率(10M–10G)自协商:千兆 AP/IoT 可直接插剩电口,省一台下联交换机。
3. jumbo 12K 有官方一手证据(电子说明书参数表),覆盖本栈 2034 档绰绰有余,9K 档(NAS↔PVE 未来路径)同样在能力内。

1. 非管理型:无 VLAN/链路聚合/端口镜像——本网络用不到这些,但未来若要 VLAN 隔离 IoT 需另想办法。
2. 2026 年新品(说明书 V1.0,2026-02 更新),长期口碑样本还少;第三方独立评测暂缺(检索未见中文首发的深度评测,官方推广文除外)。
3. 4×10G 电口满载(每口 PHY 2-3W)发热可观,被动散热下外壳温热属正常,弱电箱密闭环境建议留对流空间。
4. PoE 不支持(说明书明确)。

**适配点评(X520 DAC + AQC113 组网)**:把现网「Mac‑M4 DAC 直连」拆成两条 DAC 各插一个 SFP+ 口,现有线 investment 零损失;AQC113 是 10G Base-T PHY,插 CM996 电口即协商 10G(SFP+ 侧互不影响);小米万兆路由器 10G 电口上联进第二个电口。**8 口中 5 口被现网万兆设备占用后,还剩 2 电(多速率,接千兆 AP)+ 2 光(接 PVE 万兆升级或光回程)**——扩展位对 PVE 万兆化以及未来加光口设备都留了余地。

### 3.5 ⚠️ 反面警示:TP-LINK TL-ST1008F(8×SFP+ 非网管,¥675)——「看似最便宜」的陷阱

| 项目 | 规格 |
|---|---|
| 端口 | 8× SFP+ 光口(带 M1/M2/M3 速率模式拨动开关),非网管即插即用,钢壳自然散热无风扇 |
| **巨型帧** | ❌ **不支持**:官网 spec 页与《V2.0 安装手册》附录 A 技术参数表**均无 jumbo 条目**;TP-LINK 官方 FAQ 明文规定「spec 未声明 Jumbo Frame = 不支持,最大帧长 1522B(Baby Jumbo)」 |
| 参考价 | ¥675(2026-10,第三方渠道挂网价) |

**否决理由**:它常以「最便宜的全万兆 SFP+ 交换机」身份出现在电商搜索结果前列,价格诱人;但对本网络的目标(jumbo 透传)**是根本性否决**——1522B 上限正是现在这台哑交换机的病根,买它等于花钱换个一模一样的短板。**可视化提醒:任何候选,先查 spec 的 jumbo 行,再谈价格。**(顺带:它也有负面佐证意义——TP-LINK 非 jumbo 机连万兆电模块都限制 2 支,说明厂家对模块化电口接法的发热兼容是一贯保守口径。)

## 5. 组网适配方案(以首推 CM996 为例)

```
                       ┌───────────────────────────────┐
                       │  绿联 CM996(4×SFP+ + 4×10G电)   │
                       └───────────────────────────────┘
  Mac .120 ── DAC(SFP+) ──┤ P1 │  P5 ── 10G电 ── NAS .3(AQC113, DX4800+)
   M4 .4 ── DAC(SFP+) ──┤ P2 │  P6 ── 10G电 ── 小米万兆路由器 .1(上联)
 (预留: PVE 万兆光卡)  ── P3/P4 │  P7/P8 ── 多速率电口 ── 千兆 AP / IoT(或级联 2.5G 小交换机)
```

要点:
1. **DAC 零成本复用**:两根现行 Mac–M4 直连 DAC 拆开分别插 CM996 两个 SFP+ 口,X520 与 SFP+ 交换机口的 DAC 互连是标准用法。
2. **AQC113 直插电口**:NAS 10G Base-T PHY 与 CM996 多速率电口协商 10G 无兼容性变数(比 SFP+ 电模块方案稳一个量级)。
3. **小米万兆上联**:占第二个 10G 电口;若未来换全光核心路由,可改插 SFP+。
4. **下联弹性**:剩 2 电(多速率)可直插千兆 AP;若 2.5G 下联需求增多,级联一台 2.5G 小交换机(见 §6),现有哑交换机(1518B)退役或转做纯千兆 IoT 段。
5. **jumbo 生效路径**:哑交换机瓶颈解除后,Mac(2034)/M4(2034 推断)/NAS(16334)之间的 2034 档实验即可进行(GATE-1 流程);9000 档对 NAS↔PVE 同样具备硬件条件(PVE 侧网卡需另核)。
6. **重要提醒(承接主报告结论)**:小米万兆路由器固件无 LAN MTU/jumbo 设置项,若 Mac↔NAS 流量穿过主路由 br-lan(WAN 口之外的 LAN 桥),**主路由仍是 2034 档的第二道判据**——换交换机只解决哑交换机这一跳,主路由桥的 L2 判据仍需按主报告 §7 的 GATE-1 实测确认(建议局域网内大流量尽量走「同接 CM996 的设备间」,避免穿路由器)。

### 9.4 VPN 段特别说明:零变化(实证级,非预期)

换交换机**不改变 VPN 的任何数字**:hy2 隧道腿吞吐/包形状/隧道协议 CPU 维持现状(130.8–131.0 Mbps 形态)。这不是待验证预期,而是已有源码级实证的结论:QUIC 单包恒 ≤1452B 与 underlay MTU 完全解耦(两端 quic-go fork 的 GSO 批大小 = QUIC 包大小而非接口 MTU、接收侧无 GRO,1500 下已摊薄/9000 下不变);公网 path-MTU 1480 硬边界;1000 包 pcap 抽样 0 个 >1452。唯一关联的边际项是 §9.2 中 mihomo LAN 第一腿的 −2~5% 容器 CPU(方向可信、幅度需实测定标)。

### 9.5 结论与不确定性

**换机主要价值排序**:

1. **CPU/中断效率与 pps 摊薄**(方向确定性最高):每包处理开销下降(O(包数) 成本项 ÷1.37),Mac 软中断 490k→~358k、mihomo 容器 CPU −2~5%、PVE↔NAS 全幅档 CPU 5–15% 潜力;
2. **LAN 吞吐边际收益**(+0~5%,非保底):基线 6.94G 未触及 10G 物理上限、瓶颈不在单点包处理(4 流反而低于单流指向 NAS 接收路径),jumbo 对吞吐是「可能的小额改善」而非「解锁被压制的带宽」;
3. **VPN 零增益**(实证级,§9.4)。

**丢帧归因的残余不确定性(下单前可选甄别)**:E1 的置底判定(丢弃点=哑交换机)存在一条**无 root 设计无法排除的替代解释**——「Mac X520 RX 侧硬件长度上限跟随 en11 MTU=1500 静默截断且不留计数痕迹」。两个解释对研究决策等效(2034 档当前不可用),但影响**修复后收益的归因与幅度**。task-5-exp-report.md §2.5 给出一次性闭环甄别法:**更换交换机前**,可先做「Mac MTU 升 2034 + NAS 侧 InJumbo 计数器观测 NAS→Mac 大帧」复测——若此时 2034 帧即透传,原判定应归因 Mac RX 侧,Mac 路径(2034 档)的上述收益或显著缩小;**PVE↔NAS 9000 全幅档不受该替代解释影响**(其路径无 Apple 端点)。另注:E1 阶段拓扑前提已经用户确认(Mac↔NAS 经哑交换机、主路由 LAN 桥不在路径),换机后该路径无第二 L2 变数。
